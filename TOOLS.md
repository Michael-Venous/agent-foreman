# Manager control tool
Pass one JSON object to `python3 /home/user/Documents/code/agent-foreman/managerctl.py`.

- `{"op":"status"}`: projects, workers, assignments, resources, all events (acked too) and outbox. Use `events` for unhandled ones.
- `{"op":"sessions"}`: discover HAPI sessions, including active/ownership state.
- `{"op":"discover","runtime":"codex"}` (or claude): read native session metadata only.
- `{"op":"read","session":"HAPI ID"}`: session metadata and latest 100 structured messages.
- `{"op":"register","name":"...","repo":"/absolute/path","objective":"..."}`: register project, initially paused. Returns project ID.
- `{"op":"update","project":"ID","objective":"...","next_steps":"...","blockers":"...","checkpoint":"...","integration_owner":"..."}`: persist fields. New objective resets automatic assignment budget.
- `{"op":"resume","project":"ID"}`: explicitly return project to manager; also clears an older manual hold. Only on user instruction.
- `{"op":"pause","project":"ID"}`: stop future assignments, current turn continues. Does not clear a manual hold.
- `{"op":"complete","project":"ID","checkpoint":"evidence"}`: mark objective complete after verification, no running assignments allowed. Releases the project's resource claims.
- `{"op":"launch","project":"ID","runtime":"codex|claude","worktree":true}`: spawn worker without prompt. For parallel modifications worktree is mandatory. Returns worker ID. User-authorized full permissions are the default; pass `"permission":"ask"` for prompted workers.
- `{"op":"attach","project":"ID","runtime":"codex|claude","native_id":"exact ID"}`: register existing conversation read-only without resuming or modifying it. Never claims a live terminal.
- `{"op":"adopt","worker":"ID"}`: resume registered native conversation only after external controllers are stopped. Rejects busy native writers. Preserves original history. Will be exposed as HAPI session.
- `{"op":"assign","worker":"ID","text":"scoped task + acceptance evidence","key":"unique stable task key"}`: durable, deduplicated assignment. Never repeat with a new key to resolve uncertain delivery. Requires running project and idle worker. Returns assignment ID.
- `assign` returns a `warning` (still sent) when the instruction exceeds 1200 characters: keep instructions to the user's request plus needed context. The tool itself appends at most one short line each for reserved resources and external-only scope.
- `assign` option `"user_requested":true`: the user explicitly asked for this message. Paused/held projects, autonomous budget, busy chats (default queue; select delivery_mode for priority), an earlier unresolved task and released chats no longer refuse it. HAPI manual-stop latches (manager or worker), dedupe keys, disconnected chats and same-checkout protection still apply. It does not consume budget.
- `{"op":"interrupt","worker":"ID","pause":false}` aborts the current turn without pausing the project (default still pauses).
- `{"op":"watch","worker":"ID"|"project":"ID","mode":"events|quiet|off","note":"user preference"}`: how closely to follow a chat. `events` (default) wakes you for its events. `quiet` = hands-off: tracked (no duplicates), events kept for `digest`, no automatic wakes. `off` = back off: not scanned. The `note` is shown on every wake line for that chat (e.g. "only notify on breakthroughs").
- `{"op":"remind","in_minutes":N|"at":unix_seconds,"every_minutes":M,"worker":"ID","project":"ID","note":"..."}`: scheduled `check-in` wake (also for quiet chats); `every_minutes` ≥ 5 repeats. `{"op":"reminders"}` lists, `{"op":"cancel_reminder","id":"ID"}` cancels.
- `{"op":"digest","worker":"ID"}`: on-demand update: watch policy, running/pending state, unhandled events and the latest reply.
- `{"op":"requests","worker":"ID"|"session":"ID"}`: pending approvals/questions with question text and options. `{"op":"answer","worker"|"session":…,"request":"RID","answers":[["option or text"],…],"basis":"the user's instruction"}` answers questions (one list per question; Claude and Codex formats handled); `"decision":"approved|approved_for_session|denied|abort"` answers approvals. `basis` is required. The user can always answer in the chat instead. Question events (`input-required`) now arrive even when you have no task in that chat.
- Goals: `assign` accepts `"goal":true` to send the task as a native `/goal` (Claude and Codex). The assignment finishes when the goal completes (Codex goal status `complete`/paused/cleared, Claude `goal_status met`), not when its first turn ends; ready events alone never finish it. Objective max 4000 characters. Use for well-scoped multi-step work with checkable completion; pause/interrupt still apply.
- Assignment scope: `assign` accepts optional `"scope":"checkout|external"` (default `checkout`). `checkout` work keeps exclusive use of the worker's recorded workspace (launch directory by default): it is refused while another worker has unresolved checkout work in the same, parent, or child directory. Symlinks resolve to their real paths. Use `"scope":"external"` only for work that never reads, edits, builds, runs commands in or commits to any repository checkout (email, browser or messaging outreach). External work is not blocked by, and does not block, checkout work at that path. The worker receives an explicit external-only instruction naming the directory, and the scope is stored on the assignment. All other guards still apply: pause, manual hold, busy/approval/disconnect, one unresolved assignment per worker, deduplicated key, budget and resource claims. This is an instruction, not a sandbox (full-permission workers can technically still touch files), so never use it for work that needs the repository; give that work a worktree instead.
- `{"op":"reconcile_adopt","worker":"ID"}`: resolve a worker stuck in `adopting` from evidence only. Binds an exact active HAPI session for the registered native ID if one appeared late; otherwise returns the worker to `registered` (event `adoption-failed`) only when its `manager-adopt-ID` service is conclusively `failed` with no main PID, no process references the native ID, no live HAPI Codex runtime owns the thread, and the Codex writer lock is free. Also unbinds a `managed` worker whose HAPI session reports a different native ID (never the registered history), only after that session is inactive with no live controller or running adoption service (event `adoption-misbound`). Running, missing, or ambiguous outcomes are refused; never edit the database to clear them. Then `adopt` may be retried once.
- `{"op":"interrupt","worker":"ID"}`: pause project then HAPI turn abort (supported active sessions).
- `{"op":"claim","project":"ID","resource":"machine/GPU exact identifier"}`: exclusive recorded resource ownership. `release` with same fields releases when no running assignment.
- `{"op":"events"}`: pending supervisor events. `{"op":"ack","ids":[1,2]}` after handling.

Launches/resumes with uncertain outcomes are never blindly repeated. Status shows them for operator reconciliation. Direct user messages (including `/goal`) in manager chats do not stop management: you get one `user-steered` event per gap between your assignments; read the worker's latest turn before assigning more. If the user stops a manager chat and restarts it themselves (new controller process or new HAPI session for the same history), the worker becomes `released`: no scanning, no assignments, its open assignments marked `released`. `{"op":"manage","worker":"ID"}` resumes monitoring only on the user's explicit instruction. Chats the user opens in HAPI are never monitored; `attach` refuses a native conversation that has a HAPI chat unless `"user_requested":true` (only when the user asked). A worker completion means only a turn ended. Approvals stay in HAPI; prompted workers still require the user’s approval; full workers use the runtime’s supported bypass mode. Inactive/disconnected workers are reported, not automatically restarted mid-assignment. No elaborate scheduler: resource claims plus explicit worker instructions coordinate GPUs.

`{"op":"read_native","worker":"ID"}` reads the last 100 records of a registered native conversation without opening a controller (strings over 2000 characters are clipped). Native Codex adoption checks its writer lock. Claude adoption is deliberately conservative: stop all external Claude controllers first. HAPI-managed workers can be resumed by their registered worker ID via `adopt`, retaining the native history and updating any changed HAPI ID. A queued human manager instruction blocks automatic assignments until the manager consumes it.

For a Claude conversation that worked on a project outside its launch directory, `attach` accepts `"session_cwd":"/verified/original/cwd"`. It must exactly match the unique native history's recorded cwd. This preserves that cwd for resumption and leaves the project `repo` unchanged; it does not relocate history or change permission boundaries. Explicitly tell that worker which project repository to work in. Do not create a second writer for the same repository. Codex mismatch rejection remains unchanged. Routine adapter fixes within the user's authorized manager setup do not require another permission question; genuine controller conflicts and credentials still do.

Native Claude `/goal` is restored from session history, including goals represented by stop hooks rather than a top-level goal record. Even a read-only verification prompt may trigger the restored goal after the answer. Before treating an adopted chat as idle/paused, check its native goal state. Native `/goal` was verified through HAPI, but project `pause` only stops supervisor follow-ups: it does not cancel the native evaluator's internal loop. To stop one, use the supported worker interrupt. This now latches a manual stop; do not automatically send `/goal clear` or erase the goal afterward. Clearing a goal requires a separate explicit user request and explicit resume of message delivery. Explain that this interrupts the invocation, rather than promising a pause after an internal step. Preserve the user's objective/checkpoint separately before clearing a native goal. Do not run unbounded native goals while promising cooperative step-level pause.


Worker permission preference (user authorization 2026-10-19): default `full`, mapping to Claude `bypassPermissions` and Codex `yolo` (full filesystem access, no command approval prompts). `launch` and `attach` accept optional `"permission":"ask"` to preserve prompted operation. `{"op":"permissions","worker":"ID","permission":"full|ask"}` changes a registered worker's current HAPI session mode and persists its adoption preference. This does not grant sudo, change remote SSH account access, answer user-input questions, or expand task scope. Existing read-only registrations remain prompted unless the user requests otherwise. Manual HAPI permission changes are not continuously overwritten by reconciliation. The manager itself is not switched to bypass mode by this worker preference.

Adoption runtime ownership: Codex is adopted with `hapi codex resume NATIVE_ID --started-by runner --permission-mode MODE` (`resume ID` must come first; otherwise HAPI silently starts a new thread), the headless shared-runtime owner HAPI's runner itself uses (the `terminal` owner requires a TTY and fails under systemd). The runner ignores, never kills, unknown shared Codex roots. Claude stays `--started-by terminal`, because the runner terminates unknown runner-tagged Claude children. Adoption success requires an active HAPI session; inactive stale rows for the same history do not count, and Codex success requires the exact registered native ID. Codex import replays old prompts with import-time timestamps; their client IDs are recorded at adoption so they are not mistaken for direct user interventions (manual hold).


## Usage exhaustion recovery — 2026-10-19
The supervisor now schedules continuation for managed workers on provider usage-limit rejection (Claude reached/reset events and API errors; Codex usageLimited goals and terminal quota errors). Warnings alone do not restart chats. It waits until the reported reset plus 60 seconds; without a reset it waits one hour, backing off to six hours on repeated rejection. It resumes the same native conversation if disconnected, verifies its identity, and sends one checkpoint-aware continuation. It does not switch accounts/models or create fresh conversations to evade quota.

Recovery state is durable in `usage_recovery` and visible in `status`. Paused/completed projects, manual holds, released/off workers, busy chats, pending approvals, and another checkout owner block continuation. A new direct user message cancels the pending recovery. Unknown send/resume outcomes are retained for inspection and never blindly repeated. `resume-uncertain` requires inspecting the existing controller; no automatic second controller is spawned. The manager must not send a competing retry while usage recovery is pending. Native goals can still iterate independently of supervisor pauses, as documented above.

Validation: 65 supervisor tests, including quota timing, restart deduplication, user intervention, checkout exclusion, Codex usage states, and reconnect identity. Actual quota reset has not yet been exercised live. Today's usage audit is in `evidence/usage-audit-2026-10-19.json`; these are transcript tokens, not a provider billing/quota statement.

## Workspace and deleted-session repair — 2026-10-19

- `{"op":"workspace","worker":"ID","path":"/verified/actual/checkout"}` records the actual work directory separately from the native session launch cwd. Only change it after verifying the worker's project/history; the directory must exist and the worker must be idle without an unresolved checkout assignment. It persists across supervisor restarts and appears on workers in `status`. Assignments name this directory; both assignment and quota recovery guards use it. This does not move history or change the native launch cwd.
- `{"op":"reconcile_adopt","worker":"ID","rebind":true}` repairs an inactive/deleted binding from exact live native metadata. Process launch arguments alone are not proof of current native identity: `/clear` can remove the resume anchor. With a deleted Claude binding and no live matching session, controller process, or active adoption unit, it returns the worker to registered while preserving assignments and original history. Then `adopt` resumes that exact history. Unknown HTTP errors and ambiguous/live controllers still block.
- `{"op":"stop_cleared_controller","worker":"ID","session":"ID"}` is an explicit recovery step for an idle Claude controller whose registered HAPI row was deleted. It requires missing native identity, exact original `--resume` process ownership, latest user message `/clear`, no pending messages/approvals, and no active turn. It archives only this cleared controller; next verify exit and reconcile/adopt original history. It never treats the cleared chat as the original history.
- `{"op":"cancel_queued","assignment":"ID"}` asks HAPI to atomically cancel an uninvoked queued assignment. Only confirmed `cancelled` updates the manager record; busy/invoked/uncertain messages remain tracked.

After a repair event, inspect current assignments and delivery state before sending a continuation: an operator may already have resumed the task. Use the original stable task key for rejected pre-delivery attempts. A repair event alone is not a new user message permitting an extra busy-chat continuation.

### Adaptive reporting default — 2026-10-22 (supersedes fixed progress cadence default)

Managed chats inherit `{"enabled":true,"fallback_minutes":30,"important":true}`. Silent observation reuses scan context on SSE/periodic reconciliation; it is separate from manager/user notifications and adds no worker message or model call. Routine text/tool changes do not notify early. Only active inference/background work is eligible for unchanged status after 30 minutes (or the per-chat override). Idle/disconnected chats, input waits, manual/project holds, user-controlled sessions and unresolved usage recovery do not generate routine updates; wait states override stale activity flags. A resumed work interval starts a fresh fallback countdown. Unsent routine-only events are discarded on observed waits and rechecked before delivery, while meaningful evidence remains available. Already-delivered messages cannot be recalled. Explicit progress reminders also skip waits; user-requested scheduled tasks such as daily career checks keep their schedules. Silent read-only reconciliation/SSE observation continues to detect state changes without worker messages or model calls, and usage-reset recovery keeps its existing timers and manual-pause protections. Important evidence candidates, direct runtime turn/goal endings, and existing completion/input-needed events can notify earlier. A ready/turn-end signal is labelled for review, not claimed as whole-task completion.

- `{"op":"reporting"}` reads the persisted default; `fallback_minutes`, `important`, and `enabled` optionally change it.
- Add `"worker":"ID"` to read/set per-chat overrides. `"reset":true` removes only that chat's overrides. Existing watch modes/notes, holds/releases and explicit recurring reminders remain untouched; recurring per-chat schedules override the routine fallback, not important evidence. `quiet` keeps automatic observation notifications off; explicit reminders retain their previously requested semantics.
- `{"op":"reporting","worker":"ID","fallback_minutes":30,"replace_reminder":"ID"}` migrates an exact active reminder with the same cadence to adaptive fallback, preserving its next deadline and historical row, and suppressing its unsent generic check-ins. It does not touch running work. Do not migrate unrelated reminders.

Detection is deterministic and conservative: recent public context, explicit significant-change phrases, and reported same-unit timing/throughput changes of at least 2x (or 2x regression); previous stagnation text adds context. These are candidates for manager judgment, not a general semantic understanding or independent benchmark verification. Hypotheticals, usage warning text, tool results and reasoning are excluded from public progress text. Streaming edits to an existing message are re-evaluated; repeated identical claims are deduplicated persistently. Recent context is bounded (12 text snippets, 150 message versions, 64 reported claim hashes). Completion timestamps/notifications can lag; a lost terminal record may delay reporting. Busy managers still wait until idle; unsent observations coalesce, and there is at most one unconsumed progress/observation wake per worker. Already queued messages cannot be withdrawn.

Goal-driven turn boundaries: a fresh terminal record triggers a read-only native-goal check. An active goal suppresses routine turn-end alerts; goal-complete/terminal evidence is still presented as requiring review. `reporting.enabled` controls adaptive context/fallback notifications; ordinary completion/approval events continue to follow `watch` policy.

## Durable manual stop — 2026-10-22

HAPI **Stop** and **Archive** now persist a hub-owned pause latch before interrupt/kill. It survives hub/supervisor restarts and CLI metadata updates. Send, queued steer/retry, approval, reconnect replay, scheduled delivery, resume/reopen and plan implementation cannot bypass it. Stop attempts withdrawal of uninvoked queued and Claude ready messages before aborting; already-dispatched/indeterminate input cannot be guaranteed recalled.

The supervisor checks the latch for both the manager and target worker. A paused manager receives no wake or automatic reconnect, and cannot launch/assign/adopt/answer or run usage recovery. A paused worker cannot receive recovery or assignment, including old `user_requested:true` requests. Reminders/events remain recorded for later review; they do not unpause either chat. Project `resume`, `manage`, changing watch/reporting or old authorization do not clear a chat latch.

The user's **Resume** button or an explicitly current user-authorized `resume_chat` command clears it (`POST /sessions/:id/manual-resume`, `explicitUserResume:true`). Do not invoke that endpoint based on a supervisor event, past assignment or standing autonomy. Current explicit manager authorization uses the supported resume_chat operation described below. Clearing the latch does not itself send input, restart a controller or resume a native goal. The user can then send/reopen, and use `/goal resume` for a paused Codex goal. Ordinary interrupt-and-send stays distinct from Stop and does not create a pause latch.

Limits: project-only `pause` still lets an already-running invocation continue; use Stop to interrupt. Native terminal Esc/Ctrl-C outside HAPI does not persist this hub latch. New Codex controllers pause active/usage-limited native goals before interrupting; existing loaded controllers retain their older abort implementation until a normal user-authorized restart. Claude abort cancels the current query; its stored native goal is preserved. External jobs/subagents already launched, prompts already consumed, and native controllers outside hub delivery are not globally suspended by this latch. Never promise that Stop kills every subprocess, never clear goals to simulate a pause, and never restart a chat merely to apply this update.

## Evidence-based GPU handoff — 2026-10-22
`resource_handoff` separates a compute reservation from unfinished assignments/goals. Ordinary `release` keeps its conservative guard. Never clear a goal, invent completion, edit SQLite or Unmanage to free a claim.

```json
{"op":"resource_handoff","project":"SOURCE_PROJECT","to_project":"DESTINATION_PROJECT","resource":"main/GPU-UUID","acknowledgements":[{"worker":"SOURCE_WORKER","session":"EXACT_HAPI_ID","native_id":"EXACT_NATIVE_ID","message":"PUBLIC_REPLY_ID","quote":"Exact public text confirming this GPU is relinquished or work moved elsewhere."}]}
```

Default is read-only review (`ready`, `blockers`, `gpu`, `committed:false`). To apply the currently user-authorized handoff, submit the same fields with `commit:true`, `user_requested:true`, and `basis` quoting that current request. managerctl stamps `requested_at`; commit revalidates everything, probes the GPU again and changes owner atomically. It sends no messages/wakes, resumes/stops nothing, and preserves native goals, objectives, assignments, management, pauses and other resources. Success is `committed:true`; a blocked review is not a successful transfer. Inspect current owner after uncertain requests; never blindly repeat.

Review the quote in context: it must actually establish relinquishment of this exact GPU, not merely say a task finished or show idle momentarily. The operator attests its meaning; software checks exact public-text provenance, worker/native identity, freshness (30 minutes), no newer user/manager instruction, confirmed invocation of all outstanding assignments and no ambiguous/queued delivery or native-ready input. Every managed/unresolved source worker needs evidence. Work continuing on a different machine is permitted. Unsupported or out-of-page evidence fails closed; do not nudge workers just to obtain it.

Currently supports local `main/GPU-UUID` NVIDIA **compute** reservations only. Reads `nvidia-smi` directly, never caller-supplied process evidence; only the independently verified desktop KWin compositor is exempt by default; narrowly reviewed Chrome coexistence is described below. Graphics-only processes are outside this compute check. Remote GPUs need a future authenticated probe, not a local or caller-asserted override. Reservations coordinate agents; they do not revoke OS GPU access or guarantee a worker will obey after the snapshot. Native goals can still contain old hardware wording; latest user directions must govern, without silently rewriting goals. `settings.resource-handoff:<resource>` records the last successful review/audit.


### Reviewed incidental Chrome coexistence (2026-10-23)

The strict default still blocks every non-compositor compute client. A current explicit user allocation may preserve an existing Chrome browser while sharing its GPU. Read the default `resource_handoff` review's `gpu.processes[].incidentalIdentity`, inspect the client's real purpose, then pass:

```json
{"op":"resource_handoff","project":"SOURCE","to_project":"DESTINATION","resource":"main/GPU-UUID","acknowledgements":[{"worker":"WORKER","session":"HAPI_ID","native_id":"NATIVE_ID","message":"COMPLETED_RELEASE_REPLY","quote":"Exact actual release text"}],"incidental_clients":[{"pid":123,"resource":"main/GPU-UUID","identity":{"pid":123,"bootId":"EXACT","startTicks":"EXACT","executable":"/opt/google/chrome/chrome","executableDevice":0,"executableInode":0,"executableMtimeNs":0,"executableSize":0,"commandHash":"EXACT","parentPid":1,"parentStartTicks":"EXACT"},"purpose":"Reviewed existing PC flip Chrome GPU context; preserve browser/tabs"}],"user_requested":true,"basis":"Quote the current user allocation authorizing this coexistence"}
```

Copy **all actual identity fields**, never the illustrative zeros. managerctl supplies a fresh timestamp. Review is still noncommitting; use `commit:true` only after `ready:true` and current authorization. Chrome proof independently checks the installed executable, current user's UID, GPU-child process arguments (including Linux rewritten process titles), Chrome parent, boot/PID-start generation, executable inode/mtime/size and command hash. It is checked on both GPU probes. Wrong GPU, PID reuse, executable/command changes, missing/unknown clients, any additional compute job and stale authorization fail closed. No browser name, memory-size or global process exemption exists. This supports `/opt/google/chrome/chrome` only; other clients remain blocked.

Successful sharing retains `gpu.busy:true`, identifies reviewed `incidentalClients`, and reports `leaseMode:shared-with-reviewed-incidental-clients`; it never claims the hardware is unused. Limits: this safeguards terminal failures exposed by the runtime, not every network failure or provider-internal retry. No terminal record means no inferred automatic retry. An uncertain POST or inactive controller requires supported reconciliation. Public 429/capacity records prove upstream rejection, not account-wide quota, backend outage, region cause, or a provider-side fix. See `evidence/transient-recovery-2026-10-26/` for regression and deployment evidence.

## Provider-rejection retries are quiet and share one backoff — 2026-10-26
Automatic recovery after a 429/capacity rejection (`transient_recovery.py`) still sends at most one checkpoint continuation per attempt, but it now:
- keeps the backoff growing across one outage (60s, 2m, 4m … capped 30m) even when a person or the manager messages the chat in between (streak resets only after real model output; window 2h);
- shares a per-provider window so every Codex chat's retry waits together instead of each probing the provider separately (cleared when any chat of that provider produces real output);
- reports the first failure of an outage and every 4th repeat only (`consecutiveFailures` in the event); human-needed quota waits are always reported;
- does not raise `runtime-failure`, "turn ended" or input-receipt observations for a chat with a pending automatic retry, nor for the supervisor's own recovery message. If the retry is cancelled or stops, the failure is reported normally.
Nothing is deleted: suppressed events remain acknowledged in the events table and `transient_recovery` has the state.

### Background task evidence

Claude native task-completion notifications can nominate a single background-ended review when the chat stops reporting work; the notice includes the native task ID and completed/failed status. It does not claim the assignment finished or resume the worker. A mere count correction or successful TaskStop remains silent. Completion notices that appear only in Claude's native transcript may clear the count without appearing in HAPI's message stream; such a count change alone is not evidence for a review notification.

The activity panel treats Codex process handles as unknown unless a matching poll supplies terminal evidence. A session-wide background count cannot establish which historical handle remains live. Matching structured exit codes and leading native exit receipts identify completion/failure; a copied exit string inside program output does not. Verified local process families remain separate evidence and may not map to a specific native process handle. Neither source proves the agent intends to wait for, or review, the job; remote or detached jobs can be invisible.

### Codex native terminals and review intent

Shared Codex controllers can read `thread/backgroundTerminals/list` from their own app-server while a turn or listed terminal is active. A complete snapshot records native thread, originating item, process handle and optional OS PID, without command arguments or environment values. It refreshes every 15 seconds while active and stops polling an idle empty thread. Snapshots older than 45 seconds, partial pages, unsupported methods, different threads and inactive controllers are not treated as live. A PID belongs to the controller's machine; it is not assumed to be local to the hub. The session background count combines native terminals and locally observed process families conservatively, so overlapping sources do not inflate it; that count is not an exact count of distinct jobs.

The Activity panel matches a historical handle only when both process handle and originating native item match the fresh snapshot. Otherwise it displays native terminals separately rather than guessing a PID. A disappearance between complete fresh snapshots is evidence that a native terminal is no longer listed, not proof of a successful render, remote child exit, or completed objective. Detached processes outside that native terminal and remote jobs that outlive SSH may remain invisible. The supervisor can nominate one review event from this transition; it neither sends the worker a prompt nor restarts a job.

An active managed worker can explicitly mark **its own** currently listed native terminal for later review:

```json
{"op":"background_intent","process_id":"NATIVE_PROCESS_HANDLE","intent":"review","note":"Review the result before reporting completion"}
```

Run this through `managerctl.py` from that worker's HAPI session, after the fresh native snapshot includes the handle. Alternatives are `independent` or `unknown`; a note is optional and at most 500 characters. The supervisor binds the record to the caller, current native thread, exact originating item and process handle; it refuses another chat, stale evidence or ambiguous IDs. The annotation changes no process, turn, goal, pause, or assignment. The manager's digest exposes the current native terminals and annotations. Intent is only known if explicitly recorded; an unannotated job is not assumed to be awaited. For remote commands keep the native SSH/command session open where practical, or arrange a separately authorized remote monitor; an SSH process exiting after launching a remote detached job does not prove that remote job exited.

Existing controllers load the native snapshot capability only when they next start normally with the updated CLI. Updating the hub or web bundle does not retrofit code into running controllers; do not restart them merely for monitoring. The method is experimental and may be unsupported by older Codex versions; absence or failure leaves status unconfirmed, never a synthetic completion.

For a known detached Linux process on an already-authorized SSH host, `python3 deploy/watch-remote-process.py --host SSH_ALIAS --pid PID --identify` reads its boot ID and process-start ticks without changing it. Start the watcher as a background Codex command with the returned values:

```sh
python3 deploy/watch-remote-process.py --host SSH_ALIAS --pid PID --boot-id BOOT_ID --start-ticks START_TICKS --interval 30 --timeout 21600
```

It uses noninteractive SSH, checks only the same SSH user's process and identity, and is bounded to at most one day. Register the watcher's native handle with `background_intent` if the result needs review. Exit 0 means only that the identified process is no longer present in the remote observed process namespace; it does not establish job success. Exit 75 means connection/inspection failure or watcher expiry, so status is unknown and must not be treated as completion. It sends no signal or command to the watched process. It cannot discover an unregistered detached job, prove progress, or observe other users' hidden processes. The worker must verify PID ownership and preserve its launch evidence before identifying it; remote tools need Python 3 and usable batch SSH. No host is contacted until a worker intentionally runs this command.
