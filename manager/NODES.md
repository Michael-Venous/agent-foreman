# Node graph management

Each workspace has an overseer root. Directed ownership edges define the sessions a node may oversee; junctions organize connections, while frames and text organize the view. Frame membership and visual layout must not change conversation history or restart work.

The hub is authoritative for graph state. The supervisor validates unique ownership and cycles before projecting oversight. A parent operates only within its subtree. Read-only node_tree observation must not send prompts or resume controllers. Inspect queued-versus-invoked delivery before assuming a user correction reached a busy turn.

Idle/completed nodes remain connected until an authorized graph edit removes them. Idle edges can sleep without routine polling. Explicitly paused nodes and owners stay paused. A transient graph-read failure must not revert to classic management, drop ownership, or release resources.

Use managerctl.py with the supported node_tree, node_edit and node_graph controls documented in ../TOOLS.md. Runtime graphs, identities and assignments belong under ignored state/, not in this source tree.

Each parent decides what task, context and acceptance criteria its child needs; graph connections do not copy context. A parent can spawn a child with `node_spawn`, supplying `runtime`, `model` and `reasoning_effort` explicitly. For example, `{"op":"node_spawn","name":"Animation","directory":"/path/to/project","runtime":"claude","model":"claude-opus-5-5","reasoning_effort":"high","text":"..."}`. Codex effort is sent as `modelReasoningEffort`; Claude effort is sent as `effort`. Choose provider-supported values; launch acceptance alone does not prove the provider actually used them. The parent owns the child's output and reports relevant findings upward.

A parent can configure a direct child with `{"op":"reporting","worker":"ID","fallback_minutes":10}`. Routine reports wake the parent only while the child is running or has observed background work; `routine_enabled:false` disables them. Read `check_status`/`digest` without prompting the child. During a render, compare fresh process and render-specific evidence (for example frame counters, output timestamps, logs and exit status), not process existence alone. A quiet or unreachable process is unconfirmed, not a completed render. Ask for progress evidence as part of a normal assignment, use a scoped follow-up when safe, and escalate a hard blocker. Do not interrupt active work, replay uncertain delivery, override a manual stop, or generate repeated blind retries. Supervisory updates may wait until a busy parent can receive them; observation cannot guarantee progress or output quality.

Choose and revise the interval as work changes: rapidly changing work may need checks around ten minutes, whereas an uneventful long render may warrant several hours. These are judgment examples, not defaults; respect a cadence or disabled reporting explicitly chosen by the user. If ongoing supervision is needed, enable a suitable cadence rather than waiting for the user to prescribe a number. An interval change applies from the last delivered update or start of the current active period; an overdue shorter interval may produce a prompt observation. Important changes remain eligible immediately. Unsent routine fallback reports are recalculated; already delivered wakes cannot be recalled. Idle and paused work remains quiet.

For a `cadence-policy` event, read `{"op":"reporting","worker":"ID"}` for the user's full `cadence_instructions`. With `cadence_mode:automatic`, apply those instructions using `fallback_minutes`, then adapt on later status checks. The currently selected interval is used until you adjust it; no separate model or invisible agent guesses the cadence. `fixed` and `off` are user choices and managers cannot alter their interval or enabled state. A paused or busy owner handles policy events only when it is able to receive updates.

Each manager node can have a user-set default for its direct children, including future connections. It does not apply to grandchildren or other managers. Explicit child overrides take precedence; the user can choose “Use manager default” to remove a child's cadence override. A manager's per-child automatic interval decisions are kept separately from user overrides and discarded when the effective owner or automatic instructions change. Changing this policy never starts or messages a child. Manager policy notices are routed to the direct owner and respect its pause/busy state.

All browser nodes inherit the agent launch default: `~/.local/bin/firefox-agent-browser start`, then `fx_connect {port:2829}`. A visible agent window uses the same helper's `gui` mode. Do not substitute personal Firefox or overwrite an existing clone. Propagate this during natural task handoffs; a configuration update is not permission to restart, interrupt or unpause a node.
